The lockfile for MCP

An MCP server can rewrite the tool descriptions your agent trusts, at any time, and nothing tells you. mcpkeel pins them in a file you commit and fails the build when they change.

  • Try it
    npx mcpkeel demo
    A local server turns malicious and the build fails. No config, no network.
  • Use it
    npx mcpkeel init
    Pins every server in your MCP config into mcp.lock.
  • In CI, pinned
    npm i -D mcpkeel@0.3.0
    The tool that pins your servers, pinned itself. Then npx mcpkeel verify.

MIT licensed, no account, no telemetry. Releases are signed with npm provenance. Needs Node 22 or later.

  • init pins the definitions you reviewed in mcp.lock.
  • What the server sends today can leave that course without notice.
  • verify fails the build at the point where they part.

Three commands

  1. Pin

    mcpkeel reads your MCP config, connects to each server, and writes every tool, prompt and server instruction to mcp.lock. Read it, then commit it.

    npx mcpkeel init

  2. Verify

    In CI, mcpkeel reconnects and compares. It exits 1 if anything changed. If a server cannot be reached it exits 2 instead of passing.

    npx mcpkeel verify

  3. Accept

    When a change is one you expected, accept it. The lockfile diff then goes through code review like any other change.

    npx mcpkeel update

Add it to a workflow

Run it on pull requests and on a schedule. Servers change on their schedule, not yours.

The action can also open a pull request with the report when a server changes, so a change becomes a review to merge or close and not a red build to mute.

With sarif, each change also becomes a GitHub code-scanning alert, with a stable code and its OWASP MCP Top 10 category.

How a change is graded

The closer a change is to text your agent reads as guidance, the higher it grades. On a chart, the darkest water is the shallowest.

Critical
New text that trips a built-in check: instruction-like markup, hidden or encoded text, references to credential files, requests for the conversation or the user's keys, attempts to steer other tools or to hide actions. The checks also read the text backwards, decoded and with look-alike letters replaced, and read a tool's fields together. A published package release whose contents changed.
High
A tool description, a parameter description or the server's instructions changed. A tool was added. A tool stopped being marked read-only. The launch command now starts a different program, or the launcher now runs a different release.
Medium
A parameter was added, removed or retyped. A tool was removed. A prompt changed. The launch arguments changed.
Low
The version the server reports changed. An output schema changed.

Every change is recorded whatever its grade, with a code that never changes meaning. mcpkeel verify --fail-on high lets medium and low changes through, and mcpkeel.json records a team's decisions about findings, each with a reason.

A second reading

A server can behave when it is first asked and change afterwards. With --probe, mcpkeel reads each server two more times.

  • Later in the same session, after five calls to a tool that does not exist. This catches a server that rewrites its definitions once it has seen a few requests.
  • Under another client name. This catches a server that gives a checker clean definitions and an agent different ones.

It does not catch a server that waits for a particular day.

$ npx mcpkeel verify --probe

A model reads the change. It cannot wave it through.

The built-in checks match known patterns. With --explain, a model reads what the new text actually asks for and calls it cosmetic, functional or adversarial. An adversarial change becomes critical. A rewording that means the same thing drops to low, so a server that rewords its text every week stops failing the build.

Bring the model you trust: Claude by default, or any endpoint that speaks the OpenAI chat completions API, including a model server on your own machine, so the text never leaves it.

  • The text under review is written by whoever controls the server, so the model is a target too. It can raise a change freely, and lower one only when no built-in check fired, the text was replaced rather than added, and no new address appeared. That holds whichever model answers.
  • The text reaches the model between tags with a random id, new for every request, so it cannot pose as the end of the data.
  • Only the changed definitions are sent. Your config, environment values and headers never are, and the key is never handed to the servers being checked.
  • If the review cannot run, the stricter rule-based grades stay in place.

What gets pinned

  • Tool names, titles and descriptions
  • Input and output schemas, including every parameter name and description
  • Tool annotations, such as read-only
  • Prompts and their arguments
  • The server's instructions
  • The server's name and version
  • The release the launch command runs, with the registry's digest of it

The same servers always produce a byte-identical mcp.lock, with no timestamps, so it only appears in a diff when something changed.

What stays on your machine

  • mcpkeel has no telemetry and no account.
  • It talks to your MCP servers, to the package registries to look up the release each one runs, and, only with --explain, to the review endpoint you choose. It does not hand its keys to the servers it starts.
  • mcp.lock never contains environment values or headers. URLs are stored without credentials or query strings.
  • It has two direct dependencies: the official MCP TypeScript SDK, and a TOML reader for Codex configs.

What it does not do

It trusts what you pin.
init records whatever the server sends that day, and points out anything that trips a check. Read the lockfile before you commit it.
It checks definitions, not behavior.
It pins the release that runs, so new code fails verify, but it does not read that code. Reviewing a release before you accept it is still yours to do.
It checks when you run it.
It is not a proxy between your agent and the server. --probe narrows the gap without closing it.
It does not read tool results.
Instructions can also arrive in what a tool returns. That needs a runtime guard.
No browser sign-in yet.
Remote servers that take a token in a header work. Servers that need OAuth do not.
The built-in checks are pattern matches.
On their own they flag 50 of MCPTox's 485 poisoned tools. The lockfile catches every one as a change; the checks only decide how loud it is, and the model review reads the wording.
